The Pink Elephants Support Network: strategy note

Reach, referral and data

Smriti Bangera · 21 September 2026

The AI SEO project covers how she finds you when she searches. This note covers the other two ways people find Pink Elephants: a doctor's referral, and the data that referral work can produce, and what I'd do about both in the first ninety days.

How people actually arrive

There are three routes to Pink Elephants: she searches for it herself, her doctor refers her, or someone in her life passes it on. The SEO project is about the first route. This note is about the second, and about the data layer that sits behind all three.

The referral route matters most because it's the highest-trust moment there is: a clinician, at the point of diagnosis, telling her where to go next. Right now that depends entirely on whether the individual clinician happens to know your name.

What's already working

Worth stating plainly, because it's a genuinely strong position to build from:

  • Government already backs you as the lead organisation in this space. $4m of the ~$5.2m federal miscarriage support package went to Pink Elephants; Red Nose received $887,600 in the same round. (Dept of Health & Aged Care, March 2025.)
  • You're already inside the national health system. An accredited healthdirect information partner, listed on Pregnancy Birth and Baby, with the helpline delivered by PANDA.
  • The move off Facebook groups was the right call. The old groups couldn't track who needed what, and the platform's ad algorithm was showing baby products to grieving members. Moving to owned infrastructure is what makes any of the below possible.
  • The funding for this work already exists. The Fussell Family gift (July 2026) names digital referral pathways, personalisation and data infrastructure specifically. The mandate is already there. This is about how to spend it well.

The opening: a national guideline with a blank line in it

RANZCOG published Australia's first national miscarriage guideline in April 2025. It instructs every GP and specialist to acknowledge the loss, offer counselling, and give the patient "helpful contacts, support services" at the point of diagnosis.

It doesn't say whose contacts. The only organisation it names is Miscarriage Australia, which is an information website, not a support service. That's a real gap in the national standard of care, and it's the clearest reason to invest in the referral side specifically, rather than treating search and referral as competing priorities.

Four concrete ways into the referral pathway

None of these need a software build to start, but two of them depend on work only engineering can do first: a clinician can't refer to a page a search engine can't read, and a directory listing is only as good as the structured data behind it.

Why the site itself blocks all of this right now

The current site is an Angular single-page app: the server sends a near-empty HTML shell and the content is built client-side in the browser. Google's crawler executes JavaScript, so it still indexes the site, but most AI crawlers, healthdirect's ingestion, and simple fact-sheet scrapers don't run a full browser. What they fetch is the empty shell. That's a rendering problem, not a content problem, and it's upstream of every referral channel above.

The fix is server-side rendering (or static pre-rendering) for the public content pages, so the HTML that arrives on first request already contains the text. Angular Universal is the direct route if Pixell's stack supports it; a prerendering layer (Rendertron or a similar service sitting in front of the app) is a faster interim step if a full SSR migration isn't something Pixell can schedule quickly. I'd want that conversation with them in week one, because it gates almost everything else.

Alongside that, each page needs machine-readable markup describing what it actually is, using schema.org structured data as JSON-LD in the page head:

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "MedicalWebPage",
  "about": { "@type": "MedicalCondition", "name": "Ectopic pregnancy" },
  "audience": { "@type": "PeopleAudience", "audienceType": "patients" },
  "lastReviewed": "2026-06-01",
  "reviewedBy": {
    "@type": "Organization",
    "name": "The Pink Elephants Support Network"
  },
  "mainEntity": {
    "@type": "MedicalOrganization",
    "name": "The Pink Elephants Support Network",
    "url": "https://www.pinkelephants.org.au",
    "availableService": {
      "@type": "MedicalTherapy",
      "name": "Pregnancy Loss Helpline",
      "provider": "PANDA",
      "availableChannel": {
        "@type": "ServiceChannel",
        "servicePhone": "1300 726 306"
      }
    }
  }
}
</script>

This is the same markup that lets a search engine or an AI system correctly attribute a fact to Pink Elephants rather than paraphrasing it from somewhere else, and it's a prerequisite for the healthdirect and fact-sheet integrations above, both of which ingest structured data rather than reading prose.

Where reach and data become the same project

The routing tool isn't just a feature that happens to log things. The log is the point. Every time it helps one woman find the right next step, it also writes a line of data that doesn't exist anywhere else in Australia:

  • Support: what actually fits whom, and what's offered versus what's taken up: a live picture instead of an assumption built up over ten years.
  • Advocacy: unmet need by loss type and region, updating continuously, rather than a report that has to be re-commissioned each time.
  • Awareness: figures from the point of loss itself, not from a clinical sample months later: a dataset no one else is positioned to build.

Concretely, a routing event is a small record, written once, that never carries a name:

{ "event_id": "a routing token, not a person", "timestamp": "2026-09-21T14:32:00+10:00", "entry_channel": "referral_qr | search | word_of_mouth", "loss_type": "early_miscarriage | late_loss | ectopic | molar | stillbirth", "presented_options": ["peer_support", "counselling_directory", "helpline"], "selected_option": "peer_support", "region": "SA3 code, not a postcode or address", "session_token": "rotates, never stored against a person" }

Nothing in that record identifies her. loss_type and region are the two fields that make the AIHW-shaped reporting possible; presented_options vs selected_option is what turns "we offer support" into "here's what's actually taken up." If a phone number or email is collected later for follow-up, it lives in a separate table, linked only by a one-way token, so a breach of one side doesn't expose the other. This is what "collect need, not identity" means as an actual database design, not just a principle, and it's cheap to build this way from day one and expensive to retrofit later.

On the AI question directly: the routing logic itself should be a deterministic decision tree, not a model. Given a small, fixed set of inputs (loss type, what's already been tried, stated preference for peer vs clinical support), a rules engine is auditable, explainable to a grieving user if asked, and can't hallucinate a recommendation. The one place a language model earns its keep is tagging free-text responses (turning "I don't want to talk to strangers yet" into a structured preference), and even there, identifiers are stripped before anything leaves our systems, and any external API used carries a written no-training, no-retention data processing agreement, in line with the OAIC's October 2024 guidance on using commercial generative AI tools. That's a narrow, reviewable role, not a chatbot standing in for a person.

This is worth designing together with the Head of Data and Insights from the start rather than handing over afterwards. The schema is better for having two people in the room when it's built.

Why now: in July 2026 the AIHW published Australia's first national scoping study on pregnancy loss, and its headline finding was an absence: there's no national register, and the familiar figures (100,000 a year, 285 a day) are all the same estimate restated, not a count. That's a genuine gap a national regulator has just named, and Pink Elephants is positioned to be the one to help close it.

The first ninety days

Weeks 1–4: see what's actually happening

  • Set a real baseline: where people arrive from, where they drop off, what they never find.
  • Audit every place the Pink Elephants name already appears that isn't directly managed.
  • Talk to Pixell about what the site can and can't be changed to do.
  • Write down the position on privacy, consent and data retention before any new field is collected.

Weeks 3–9: open the referral pathway

  • Start with the free, fast routes: CPD accreditation and the fact-sheet libraries.
  • Correct and complete the national directory listings.
  • Form a small GP advisory group. It's the credential that makes the rest of this easier.
  • Build a clinician-facing page focused on referral, not just information.

Weeks 8–13: route, and start counting

  • Build the support-matching tool, reviewed by peer companions before it goes live.
  • Design consent and data handling together with the Head of Data and Insights.
  • Check capacity before driving more traffic. More people arriving only helps if support can hold.
  • First readout against the week-one baseline.

Ethics, privacy and security

A list of Australian women who've had a miscarriage, with contact details, is about as sensitive as data gets. Three things I'd hold to from day one:

Automation helps someone find a human faster: it never replaces one

Two well-documented nonprofit failures (a US eating disorder charity's chatbot, and a peer-support platform that used undisclosed AI-generated replies) both did real, lasting damage by putting unsupervised automation between a vulnerable person and a human. AI belongs behind the scenes, helping our people respond faster and better, never in front of someone on the worst day of their life. And when something is automated, we say so.

Collect need, not identity

The system doesn't need her name to route her correctly. If need is held separately from identity from the first record (the schema above), the dataset is publishable, shareable with researchers, and structurally much harder to turn into the kind of breach that damages a charity. This is much easier to build in from the start than to retrofit later.

In practice, on the Salesforce side that means three concrete decisions, not just a policy statement: identity fields (name, phone, email) get field-level encryption rather than sitting in plain text alongside case notes; a scheduled purge job enforces the retention schedule automatically, so "we said we'd delete it after two years" doesn't quietly depend on someone remembering to; and every read of an identified record is logged, so if something does go wrong, we can say exactly who accessed what and when, which is also what the Notifiable Data Breach scheme expects an organisation to be able to produce.

It signposts: it never diagnoses

No scores, no risk ratings, no "you may have complicated grief." That's also what keeps the tool outside medical device regulation, a deliberate design choice rather than just a legal workaround.

The legal floor, briefly

  • Miscarriage is health information, which counts as sensitive information under the Privacy Act. Collecting it needs consent that's specific and clearly given, not a box ticked alongside a newsletter signup.
  • The usual small-charity exemption from the Privacy Act likely doesn't apply here, because organisations that assess and record health information are covered regardless of size. Opting in voluntarily is free, and turns an argument we'd probably lose into a trust signal instead.
  • Vendors are a real risk: the Australian Red Cross Blood Service breach (2016) exposed 550,000 people's data, including pregnancy history, because of a contractor's mistake. The organisation was still held responsible.
  • Keeping data longer than needed is the biggest multiplier of harm if something does go wrong. A clear retention schedule, decided early, is one of the highest-value things a small team can do.
